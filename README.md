# Remember 记账

本地优先的 Flutter 记账应用，Android 支持支付通知自动记录，iOS 手动记账。数据仅保存在本地设备，不上传服务器。

## 功能

- 本地优先：SQLite 本地存储，不依赖网络
- 自动记录（Android）：监听支付类通知，自动生成账单，支持手动修改且不会被后续通知覆盖
- 跨来源去重：微信支付和银行各通知一次的同一笔扣费，只记一笔
- 账单导入（Android/iOS）：导入微信 / 支付宝官方账单文件，补记 App 内转账等没有通知的消费
- 手动新增/编辑/删除：跨平台统一
- 统计：日/月收支、分类排行、近 30 天趋势
- CSV 导入导出：Settings -> 数据管理
- Material 3 现代界面：统一圆角与控件主题，支出/收入用语义色（深色模式自动适配）

## 界面

三个主页面按「先看总量、再看明细」的顺序组织：

**账单页**

- 顶部渐变概览卡：今天支出 / 本月支出大数字，下面一行是支出、收入 chip 和笔数，
  口径和下面列表完全一致（同一套筛选条件算出来的）。
- 搜索框：搜分类、备注或金额。
- 筛选：全部 / 支出 / 收入，加上分类 chips。
- 列表**按日期分组**，组头是「今天 / 昨天 / 前天 / 周X / M月D日」，
  右边带当天的收支小计，一眼能看出哪天花得多。
- 每一条：左侧是分类图标 + 分类色（颜色固定，不再随机），中间是分类名、
  时间、来源与摘要，右边是金额。
- 列表可以左右滑：**左滑删除**（删完立刻给一个「撤销」，误删能救回来），
  **右滑编辑**；长按走确认框。旧版本的滑动删除是坏的——划完必然弹回原位。
- 空的两种情况分开说：「还没有账单」和「没有匹配的记录」。

**主题与配色**

- 支出 / 收入用的是 App 自己的语义色（`lib/theme/app_theme.dart` 里的 `AppColors`），
  不是写死的 `Colors.red` / `Colors.green`。红绿在深色底上本身就难分，
  写死的那套在暗色模式下又刺眼、又看不清数字。
- 分类色表保持不变（用户靠颜色认分类），但深色模式下会自动提亮、略降饱和，
  保证黑底上不糊。`test/app_theme_test.dart` 钉住了这件事。
- 圆角、卡片、输入框、弹窗、底部弹窗、SnackBar、底部导航、FAB 全 App 统一，
  不再是每个页面各写各的。

**流畅度**

- 账单列表用 `ListView.builder`，只构建屏幕内的行（早先是 `ListView(children:)`，
  几百条账单一次性全建，直接掉帧）。
- 筛选、分类、分组、概览数字合并成一次遍历算完并缓存复用
  （早先是三个 getter，每帧被调三四遍，每遍都重新拼字符串）。
- 搜索框 140ms 防抖，边打边筛不卡。
- `lib/utils/frame_monitor.dart` 是开发期专用的掉帧监视器（release 包里不生效），
  用 `SchedulerBinding` 统计帧时长和 buildDuration——
  `dumpsys gfxinfo` 统计不到 Flutter 的帧，它走的是自己的引擎渲染。

**统计页**

- 月份切换条，白底细线，不用刺眼的高亮色块。
- 月度概览：本月支出 / 本月收入 / 今日支出 / 今日收入。
- 支出分类占比饼图 + **分类排行列表**（色点、名称、百分比、金额、占比条），
  按金额从多到少排——比光看饼图好判断钱花在哪了。
- 近 30 天趋势图，网格改成淡横线。

**设置页**

- 分「数据管理」「账单去重」「自动记账」「危险操作」「关于」几块，
  「清空所有账单」单独放在危险操作区，不会误点。
- **自动记账**默认只显示三样东西：现在是什么状态、有异常时的一行提示、
  「重新连接监听服务」按钮。状态一句话说清（`服务已连接 · 最近收到通知 刚刚`）。
- 诊断细节（保活重连次数、上次连接时刻、国产 ROM 的自启动/电池白名单入口）
  全部收进**「诊断详情」折叠区**；「最近收到的通知」也单独折叠。
  这些东西平时用不上，摊开只是噪音。
- 状态行是「标签 : 值」两段式，值靠右对齐。
  早期版本一行里塞了标签、弹性空白、值、补充说明四段，
  补充说明一长就把右边的值压成几像素宽——「已连接」被挤成竖着的
  「已连 / 接」。`test/settings_layout_test.dart` 用最长的那组数据钉住了这件事。
- 「疑似僵死」的告警阈值对用户放宽到 2 小时：内部保活逻辑仍用 30 分钟
  （和原生层一致），但拿 30 分钟直接报警会误报得厉害——
  一两个小时没收到任何通知太正常了。
- **「后台常驻监听」开关**：打开后 App 会在通知栏留一条常驻通知，
  进程被系统回收后由系统重新拉起。关掉之后退到后台可能被系统清理。
  设置页会分开显示「开关开没开」和「服务在不在跑」——
  进程被清掉之后开关还是开着的，只看开关会以为一切正常。
- 「诊断详情」里还有三行：后台常驻服务（运行中/未运行）、
  自动修复（上次什么时候做了什么）、上次进程结束（时间 + 原因）。

## Android 支付通知

1. 打开系统设置 -> 通知使用权 / 通知监听器
2. 开启 “Remember 记账” 的通知监听权限
3. 常见支付 App 的关键字已内置匹配，可在设置中查看是否已开启

### 工作方式

- 监听服务由系统绑定维持，**App 未运行时收到的支付通知不会被丢弃**：事件会先写入
  SharedPreferences 缓存（最多 200 条），下次打开 App 时自动补记，并还原通知的原始
  发生日期，而不是记成补记当天的日期。
- 同一来源 + 同金额 + 同收支方向的通知在 10 分钟内只记一条，避免重复记账。
- 跨来源（支付平台 ↔ 银行）另有一套更严格的判重，见下节「重复账单」。
- 金额提取规则（见 `android/.../PaymentParser.kt`）：
  - 优先从 `¥/￥/RMB + 数字` 或 `数字 + 元` 中提取，支持千分位与全角符号；
  - 一条通知里出现多个数字时，取**离收支关键词最近**的那个，
    所以「余额 1000.00 元，付款成功 51.51」会记成 51.51 而不是余额；
  - 裸数字兜底只认「两位小数」，且排除日期形态（`2024.10.05` 不会被当成 2024.10）。
- 方向判定：先剥掉「微信支付 / 京东支付」这类品牌名再匹配关键词，
  避免标题里的「支付」二字把收款通知误判成支出。
  覆盖「支付成功 / 付款成功 / 支付 / 付款 / 消费 / 支出 / 扣款 / 转出 / 提现 / 交易成功」等支出词，
  以及「收款 / 到账 / 到帐 / 入账 / 存入 / 收入 / 红包 / 退款 / 收到转账」等收入词。
- 识别与真实 App 文案对齐，实测可解析：
  - 微信付款「微信支付 / 你于2026年10月20日,使用付款功能交易成功支付12.50元」
  - 微信收款「微信支付 / 微信收款 12.50元」
  - 微信转账「微信支付 / 收到转账 12.50元」「微信支付 / 转账到账 12.50元」
  - 微信提现「微信支付 / 提现到零钱 12.50元」
  - 支付宝「支付宝 / 你有一笔支出 12.50元」「支付宝 / 付款成功 12.50元」
  - 银行「招商银行 / 交易成功 12.50元」「招商银行 / 您尾号8888的储蓄卡…消费 12.50元」
  - 银行入账「工商银行 / 入账 12.50元」
  - 银联 / 抖音 / 美团等「支付成功 12.50元」
- 匹配只看**通知正文**，不绑定具体 App：任何 App 只要发出含上述关键词与金额的通知，
  都会被自动记账，`sourceApp` 记录来源包名。

> 局限：正文里既没有收支关键词、也没有金额正负号的通知（例如只有「¥12.50」）
> 会被整条忽略。方向猜错会往账本里塞一条错误的收支，漏记可以由用户手动补，
> 因此这里选择宁缺毋滥。

### 后台常驻与自愈

用户反馈「时间久了监听就没了」。查下来根因不在解析，而在**保活机制在空转**：

- 旧的自动保活每 15 分钟调一次 `NotificationListenerService.requestRebind()`。
  这个 API 有个众所周知的毛病——**监听服务已经被系统解绑之后，它经常什么也不做**
  （官方 issue 长期未修）。真正管用的是「禁用再启用组件」，
  但那一招之前只在用户手动点按钮时才走。
- 于是 App 自己在后台每 15 分钟空转一次，在「绑定僵死」这种最常见的故障上
  永远修不好。用户看到的就是「刚装上好使，过几天就再也收不到了」。

现在分三级处理，代价从小到大：

| 情况 | 判据 | 动作 |
| --- | --- | --- |
| 服务还活着 | 最近收到过任意通知 | 只 `requestRebind`（无副作用，廉价） |
| 没证据说它死了 | 只是很久没动静 | `requestRebind`（无副作用） |
| **有硬证据说它死了** | 进程被杀后再没连上 / 系统明确断开 | **重置组件**（有副作用，限频） |

「硬证据」只有两种（`ListenerHealth.shouldEscalate`，有 JVM 单测覆盖）：

- 进程被杀过，之后再没连上过；
- 系统明确回调过断开，过了宽限期还是没连上。

**刻意不拿「多久没收到通知」当证据**——用户安静的手机上半天没通知太正常了，
误伤一次反而可能被系统拉黑，比不治更糟。重置组件限频 6 小时一次。

#### 四条腿

| 机制 | 作用 | 抗清理能力 |
| --- | --- | --- |
| 常驻前台服务 | 进程优先级高，`START_STICKY` 让进程被回收后系统重新拉起 | 强：国产 ROM 的「一键清理」一般会跳过有前台服务的 App |
| 通知监听服务本身 | 由系统绑定 | 系统行为，App 控制不了 |
| 保活闹钟（15 分钟） | 把进程拉起来做一次体检 | 弱：容易被清理策略连闹钟一起干掉 |
| JobScheduler 任务（30 分钟） | 同上，但由系统托管、跨重启保留 | 中：进程被杀后系统会重新调度它 |

#### 做不到的事（必须如实告诉用户）

用户在系统设置里点「强行停止」之后，Android 会把 App 标记为 stopped，
此时**不跑任何组件**：闹钟、后台服务、Job 全停，通知监听也不会被系统绑定。
**这是平台级的硬限制，任何 App 都绕不过**，唯一的办法是让用户重新打开一次。

App 用 `ApplicationExitInfo`（Android 11+）查出上次进程是怎么没的，
在设置页明确提示「上次被强行停止过，系统不会自动恢复监听，请重新打开一次 App」，
而不是让用户干等。设置页的「诊断详情」里也有「上次进程结束」这一行。

> 局限：模拟器是标准 Android，验证不了 MIUI / EMUI 清理助手的具体行为。
> 国产 ROM 上还需要实机确认。

### 后台持续监听能力（实测）

在 Android 14 模拟器上实测：

| 场景 | 结果 |
| --- | --- |
| App 退到后台 | 持续监听 ✅ |
| App 从未被打开 | 持续监听，事件进原生缓存，下次打开自动补记 ✅ |
| 设备重启 | 系统自动重建监听服务，**不需要用户手动打开 App** ✅ |
| 被「强行停止」 | 系统同样会重新拉起监听服务 ✅（但见下方局限） |

局限：系统重新拉起监听服务需要几秒，这段时间里到达的通知会丢失。
另外部分国产 ROM（MIUI / EMUI / ColorOS 等）有额外的自启动与电池优化限制，
需要手动允许自启动、并把本 App 加入电池优化白名单。

### 监听服务被解绑后的自愈

Android 上有个已知缺陷：**通知监听服务被系统解绑之后，不会再自动绑回来**。
国产 ROM 上尤其明显。表现很迷惑——系统设置里明明还勾着、
App 里也显示「监听服务：已连接」，但实际上一个通知都收不到，
于是支付通知再也没被自动记账。典型的现场是「刚装上 1、2 小时有效，之后就废了」。

针对这个问题，App 做了两层自愈：

**自动层（全程无副作用）**

- 每 15 分钟排一次保活闹钟（`setAndAllowWhileIdle`，Doze 下也能被唤醒），
  到点把进程拉起来请求系统重新绑定监听服务；
- 监听服务一旦断开，立刻请求重新绑定；
- App 回到前台时请求重新绑定并重新排闹钟；
- 设备重启、App 升级后自动重排闹钟并重绑。

**手动层（用户点按钮才走）**

设置 → 自动记账 里的 **「重新连接监听服务」** 按钮。它分两步，先轻后重：

1. 先用官方的 `requestRebind` 请求重绑（无副作用），等几秒看有没有连上；
2. 只有确实没连上，才禁用再启用监听组件，逼系统丢掉旧绑定重新建立
   （这一步有副作用，系统可能临时拉黑反复绑定失败的监听器，所以不自动做）。

判断「绑定到底还活着没有」用的是**最近有没有还在收到通知**，
而不是 `onListenerConnected` 事件——因为绑定本来健康时，
`requestRebind` 并不会再次触发这个事件，拿它当判据会误判。

设置页因此会分别显示两个时间：

- **最近收到通知**：任何一条通知都算（含聊天消息），用来判断服务死活；
- **最近支付类通知**：只有疑似支付类的才算。

当「系统说已连接，但已经很久（超过 30 分钟）没收到任何通知了」，
设置页会直接弹出橙色告警，提示绑定可能已经僵死，点一下重连按钮即可。

### 「有通知但没记账」怎么查

「通知监听已开启」只说明**系统设置里勾上了**，不代表监听服务真的活着，
也不代表通知文案被识别。为了不让排查变成黑盒，App 自带了一套诊断：

- 设置 → 自动记账 里会分别显示三件事：
  1. **有没有授权**（系统里的通知使用权）；
  2. **监听服务有没有真的连上**（原生层记录连接/断开时刻）；
  3. **最近收到的通知原文**，以及每一条**为什么没被记**——
     是「判断出了收支方向，但没找到金额」还是「没有收支关键词，也没有金额正负号」。
- 首页顶部也会在「未授权」或「已授权但服务从没连上过」时弹出告警条，点一下直达设置页。
- 切到「设置」页签时会自动拉一次最新数据，不用记得点「刷新」。
- 诊断信息里还提供「允许自启动」「电池优化白名单」「应用设置」三个一键入口，
  国产 ROM 上这两项是通知监听能否工作的关键。

### 通知没被自动记账，可以一键补记

有些支付通知只写了「¥31.31」这类金额，没有「支付/收款/到账」这类方向词，
App 判断不出是收入还是支出。这时**不会自动记账**——猜错方向会往账本里
塞一条错误的收支，比不记还糟。

但金额本身是明确的，所以在诊断列表里那条通知下面会直接给出两个按钮：

- **记为支出 ¥31.31**
- **记为收入 ¥31.31**

点一下就按普通账单落库（分类自动推断、判重照常生效，同一笔不会记两次），
之后该条通知的按钮会消失。

诊断数据只存在本机（最近 50 条通知原文），不联网、不上传。

## 重复账单

微信支付会发一条「付款成功 ¥31.31」，绑定的银行又会发一条
「您尾号8888的储蓄卡于…消费支出人民币31.31元」——**说的是同一笔钱**，
但旧的去重逻辑是按来源包名匹配的，两个包名不一样，永远互相看不见，
于是账本里就出现两条。

现在的判重分两种情况：

| 情况 | 窗口 | 规则 |
| --- | --- | --- |
| 同来源 | 10 分钟 | 同包名 + 同金额 + 同方向 → 只记一条（系统重复推送） |
| 跨来源 | 10 分钟 | **支付平台 ↔ 银行**，或**同一家银行** + 同金额 + 同方向 → 只记一条 |

### 认银行：从「是不是银行」升级到「是哪家银行」

用户反馈「账单依旧会重复记录」——场景是**一条微信/支付宝、一条银行 App，
金额完全一样，时间差 5 分钟以内**。按上面的规则这本该判重成功，
查下来根因是：**那个银行 App 没被认出来是银行**。

原先认银行只靠包名，而包名表只有 18 家。信用卡 App（掌上生活、动卡空间、
口袋银行）、地方银行、民营银行、数字银行都不在里面——
用户装的银行 App 一旦认不出来，它的通知就被判成「其它」，
于是「支付平台 ↔ 银行」配不上，同一笔被记成两笔。

但**银行通知的正文里几乎总会写银行名**：
- 银行短信：「【招商银行】您尾号8888的信用卡于…」
- 微信支付：「…使用招商银行(1234)信用卡支付31.31元」

所以现在从正文里抽银行名，两条通知里出现**同一家银行**就是「同一笔」的强证据：

- 认得出银行名 + 认得出同一家 → 合并（不再依赖角色配对）；
- 微信支付通知即使正文带银行名，**角色仍然是 platform**
  ——靠包名判定，不能靠正文（微信通知会写「信用卡」，用关键词会误判）；
- 两家**不同**银行 → 不合并（那多半是两笔真交易）。

跨来源窗口也从 5 分钟放宽到 10 分钟：银行 App 的推送经常延迟，
用户反馈过「差个七八分钟还是记了两笔」；身份判据变强了，
时间窗就可以放宽一点换回召回。

「清理已有重复账单」用的是同一套判据，所以历史重复也能一起清掉。

跨来源判重要先知道「谁是支付平台、谁是银行」，判定**以包名为准**，
正文只作短信 App 的补充判据：

- 支付平台：微信、支付宝、云闪付、QQ、京东、美团、淘宝、拼多多、抖音等；
- 银行：工行、建行、招行、农行、交行、光大、中信、华夏、邮储、平安等 18 家；
- 银行短信：短信 App 的包名只能说明「这是条短信」，得看正文里有没有
  「储蓄卡 / 借记卡 / 尾号 / 账户余额 / 代扣」这类银行短信特征。

正文关键词**不能**用来判平台通知——微信支付的完整版可能写
「使用招商银行(1234)信用卡支付31.31元」，含「信用卡」，
用关键词判会把支付平台通知误判成银行通知。所以「信用卡」也不算银行特征。

两条刻意的保守设计：

1. **只合并「平台 ↔ 银行」这一种配对**。两个陌生 App 之间即使金额时间一样，
   也可能是两笔真交易，不合。合并错一次用户平白少一笔账，漏合并一次顶多
   多一笔、用户自己能删。
2. **认不出来的包名一律不参与合并**。

### 设置

设置 → **账单去重**：

- **跨来源自动去重**（默认开启）：关掉就退回旧行为。开关状态存在数据库里，
  重启 App 不会丢。
- **清理已有重复账单**：扫一遍历史记录，把已经记进去的重复项删掉。
  手动记的、用户编辑过的一律不动；每组重复只保留最早的那条。
  删之前会弹确认框，告诉你要删几条。

## 微信/支付宝账单导入

通知监听有个覆盖不到的场景：**在微信、支付宝 App 内部发起的转账**。
这类操作平台并不发系统通知（结果只在 App 内部页面展示），
所以无论怎么调通知监听都记不下来，只能从官方账单文件补。

入口：设置 -> 数据管理 -> **导入微信/支付宝账单**（旁边有「?」按钮看导出路径）。

支持的格式：

| 来源 | 文件 | 编码 |
| --- | --- | --- |
| 微信 | 账单下载得到的 zip（里面是 xlsx），或电脑版导出的 csv | UTF-8（带 BOM） |
| 支付宝 | 交易记录明细 csv，或对账单 xlsx | GBK / UTF-8 |

导出路径（App 内）：

- 微信：我的 -> 服务 -> 钱包 -> 账单 -> 右上角「…」-> 账单下载，选时间范围
- 支付宝：我的 -> 账单 -> 右上角「…」-> 账单导出 / 交易记录证明

导入规则（`lib/utils/bill_parser.dart`）：

- 自动识别表头，跳过官方导出文件前面的说明文字和结尾的分隔线；
- 作废行不导入：微信以 `/` 开头的行，或状态含「作废 / 已关闭 / 交易关闭 / 支付失败」的行；
- 「不计收支」的行不导入：零钱充值、零钱提现、余额宝转入转出 —— 那是自己账户之间的搬运，不是消费；
- 退款行一律记成**收入**（钱回到自己账上），与原消费相抵；
- 分类沿用通知记账同一套关键词表（`lib/utils/category_guesser.dart`），
  转账 / 还款 / 充值这类归到「转账」；
- 判重优先用平台交易单号（微信「交易单号」/ 支付宝「交易号」），
  同一份账单导入两次不会产生重复；没有单号时退回
  「同钱包 + 同金额 + 同方向 + 2 分钟内」的弱匹配，通知已经记过的那笔不会被再记一次。

`tool/sample_bills/` 放了两份按官方格式生成的样本文件（微信 UTF-8 BOM、支付宝 GBK），
既用于单元测试，也可以直接拿来在真机上试导入。
